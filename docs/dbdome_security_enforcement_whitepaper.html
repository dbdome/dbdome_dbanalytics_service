Security Enforcement

Protection that lives inside the database — not in front of it.

DBDOME discovers sensitive data, then enforces it with the database's own controls: native masking, roles, and an encrypted token vault. No inline proxy, no query-path latency, no bypass surface — every action discovered, applied, audited, and scored from one on-prem appliance.

Agentless collection In-database enforcement Grafana-native dashboards Audited & reversible PCI-DSS · HIPAA · GDPR
The model

One pipeline: discover, classify, enforce, prove.

Most tools bolt masking onto a network proxy that every query must traverse. DBDOME takes the opposite stance — it watches the estate out-of-band, finds the sensitive columns, and then reaches into the database to apply the control the situation needs, using mechanisms the engine already enforces on its own. What follows is exactly how each of the six enforcement capabilities is implemented, and how that architecture compares to a proxy-based platform such as DataSunrise.

Six capabilities

Security enforcement, end to end.

Discover & classify

Sensitive Columns Explorer

Two discovery engines find PII without a single manual mapping. Name-based scanning matches ~40 tokens (SSN, IBAN, card, email, DOB, medical…) across the catalog; value-based discovery samples freshly-collected data and confirms with format regexes — a match on both name and value scores 100% confidence.

Findings land in log.discovery_candidates and monitoring.sensitive_schema, tagged by PII category and confidence. Columns pending review >24h raise a GDPR alert automatically.

Access control

Role-Based Access Control (RBAC)

One click provisions a complete least-privilege model: a pre-change database backup first (the restore point), then four schema-scoped roles — db_readonly, db_dataentry, db_manager, db_report_viewer — plus a server role srv_dba, each with a mapped, policy-checked login.

Provisioning is idempotent (roles created only if missing, grants re-applied harmlessly) and every step is written to metrics.rbac_log. The same recorded backup is the estate's global revert path.

Anonymize

Anonymization

For non-production copies: suppress, substitute, generalize, shuffle, hash, or format-preserving “realistic” replacement that keeps length, case and separators (cards stay card-shaped, emails stay email-shaped) while destroying the link to the real subject.

It runs as a safe, staged workflow — anonymize_pre operates on a timestamped copy (original untouched) and mirrors it to Postgres for review; anonymize_actual swaps it live; anonymize_confirm archives the original. Every action → metrics.dp_log.

Mask · static

Static Data Masking

Permanently overwrites the stored values in a lower environment — null, default, fixed:<value>, shuffle, or partial(p,"pad",s) — and reports the affected row count. The column is resolved and bracket-validated to keep the operation injection-safe.

Destructive by design and clearly separated from the live-data controls; recorded to metrics.dp_log and revertible from the pre-change backup via restore_database().

Mask · dynamic

Dynamic Data Masking

Non-destructive protection for production: the real value stays in the table and is masked on display for any principal without UNMASK. DBDOME applies the database's native ALTER COLUMN … ADD MASKED WITH (…), validating the function against an allow-list (default(), email(), random(), partial()). It is idempotent (drops an existing mask before re-adding) and live — no restart.

An auto-mask engine can apply it straight from PII detection (gated by a masking_dry_run switch), and the Explorer offers authorized one-click masking with real-vs-masked previews. Reverse instantly with revert_dynamic_mask() — plaintext is never touched.

Tokenize / vault

Tokenization

Replaces a column with a random 32-char surrogate and stores the true value encrypted in a separate vault database, TokenVault.dbo.Tokens — so the source database holds neither the plaintext nor the key. Encryption is passphrase or AES-256; a usp_Detokenize proc is granted only to the payment-processor role.

Staged like anonymization (tokenize_pre → tokenize_actual) and reversible by design: revert_tokenize() joins tokens back to their decrypted values. Result-set tokens are stable surrogates keyed by hash in config.masking_tokens. All audited to metrics.dp_log.

The architectural difference

Enforced by the database — or intercepted by a proxy.

This is the choice that shapes everything else: latency, availability, the bypass surface, and what happens the day your security tool is offline.

DBDOME · in-database

Controls live where the data lives

app→ database (mask · role · vault) ⇠DBDOME out-of-band
  • Zero query-path latency. Nothing sits between the app and the database; DBDOME observes and applies, it does not relay traffic.
  • No bypass surface. Masking, roles and tokens are enforced by the engine for every session — direct connections included.
  • Survives downtime. If the DBDOME service stops, the controls remain in force — they are part of the database, not a gateway in front of it.
  • Nothing to re-route. No connection strings to repoint, no proxy cluster to size and keep highly-available.
Proxy platform · e.g. DataSunrise

Controls live in a gateway on the wire

app→ proxy (intercept · rewrite) →database
  • Every query is relayed through the proxy, which adds a network hop and a component to scale and keep available.
  • Dynamic masking is applied in transit — it protects traffic that goes through the proxy; the proxy firewall must also close off direct paths.
  • The gateway is the enforcement point. If it is bypassed or down, in-transit masking is not applied.
  • Clients must be pointed at the proxy, and it becomes a tier to secure and operate in its own right.

Why DBDOME

Five reasons teams choose in-database enforcement.

01

No new tier on the wire

Nothing to insert between apps and databases — so no per-query latency, no proxy cluster to size, and no connection strings to repoint across the estate.

02

No bypass surface

Masks, roles and tokens are enforced by the engine for every session. Protection isn't conditional on traffic passing through a gateway.

03

Fails safe

Because controls are part of the database, they stay in force even if the DBDOME service is stopped for maintenance.

04

Safe by construction

Backup-before-change, staged copy→switch→archive, dry-run switches, allow-listed mask functions, and full audit to dp_log / rbac_log / masking_log.

05

One appliance, whole lifecycle

Discover → classify → enforce → monitor → alert → score for PCI-DSS, HIPAA and GDPR — without stitching together separate products.

A fair word on DataSunrise

DataSunrise is a mature, broad, multi-engine platform, and its proxy model has real strengths: a single in-line policy point across many database technologies, format-preserving encryption and synthetic data, and context-aware rules coupled with a database firewall and SQL-injection defenses at the gateway. Where a centralized in-transit choke-point across heterogeneous engines is the goal, it fits well. DBDOME makes the opposite architectural bet — push enforcement into the database itself — which is the better fit for teams that want native controls, zero added latency, no bypass surface, and discovery-to-compliance unified in one on-prem appliance.
